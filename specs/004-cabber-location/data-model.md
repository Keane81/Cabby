# Data Model: Каббер — публикация текущего местоположения (v1)

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Research**: [research.md](./research.md)

## 1. Таблица `cabber_location` (БД `location`)

| Колонка | Тип | Ограничения | Смысл |
|---|---|---|---|
| `id` | `bigint generated always as identity` | PK | Порядок вставки; тай-брейкер при равных `received_at`. Наружу не отдаётся |
| `cabber_id` | `uuid` | `not null` | Идентификатор каббера из `auth`. Внешнего ключа нет: БД другого сервиса недоступна по границе владения. Целостность поддерживает gateway, который берёт значение из подтверждённой сессии |
| `latitude` | `double precision` | `not null`, `check (latitude between -90 and 90)` | Градусы, округлено до 7 знаков |
| `longitude` | `double precision` | `not null`, `check (longitude between -180 and 180)` | Градусы, округлено до 7 знаков |
| `received_at` | `timestamptz` | `not null` | Момент приёма, часы сервиса `location` (FR-006) |

Индекс: `cabber_location_cabber_received (cabber_id, received_at desc, id desc)`.

Инварианты:

1. Строка неизменяема: приложение не выполняет `update` и `delete` над таблицей (FR-005). Роль `location` в БД владеет таблицей; ограничение прав до `insert`/`select` отложено вместе с политикой хранения, потому что миграции идут от той же роли.
2. Текущее местоположение каббера — строка с максимальной парой `(received_at, id)`; у нового каббера строк нет.
3. Принятая строка всегда соответствует диапазонам и конечности значений: проверка на двух уровнях — сервис и `check`-ограничения таблицы.

## 2. Логические схемы

**REST (gateway)** — `POST /cabber/location`, `Authorization: Bearer <access_token>`:

```json
{ "latitude": 55.7558, "longitude": 37.6173 }
```

Ответ `201`: `{ "received_at": "2026-10-01T09:30:12.345678Z" }`. Остальные ответы — унифицированный конверт ошибок 002 (`{"error":{"code","message","field?"}}`).

**gRPC `location.v1`** — см. [contracts/location.proto](./contracts/location.proto). **gRPC `auth.v1`** — дельта в [contracts/external-and-auth-changes.md](./contracts/external-and-auth-changes.md).

## 3. Валидация

| Поле | Правило | `reason` |
|---|---|---|
| `latitude`, `longitude` | отсутствует в теле | `missing` |
| то же | не JSON-число (строка, `null`, объект) | `not_a_number` |
| то же | не конечное число | `not_a_number` |
| `latitude` | вне `[-90, 90]` | `out_of_range` |
| `longitude` | вне `[-180, 180]` | `out_of_range` |
| тело | не JSON, не объект, больше 1 КиБ | без `field` |

Порядок проверки при нескольких недостатках: `latitude`, затем `longitude`. Значения на границах и `0, 0` допустимы. После проверки значения округляются до 7 знаков после запятой.

## 4. Матрица ошибок

| Ситуация | gRPC `location` / `auth` | HTTP | `error.code` |
|---|---|---|---|
| Токен отсутствует, неверен, отозван, истёк или простаивает | `auth`: `UNAUTHENTICATED` | 401 | `unauthorized` |
| Некорректные координаты или тело | `location`: `INVALID_ARGUMENT` + `ErrorField` (или разбор в gateway) | 400 | `invalid_request` (+ `field`) |
| `auth`/`location`/БД недоступны или дедлайн | `UNAVAILABLE` / `DEADLINE_EXCEEDED` | 503 | `service_unavailable` |
| Прочие сбои | `INTERNAL`, `UNKNOWN` | 500 | `internal_error` |
| `GET`/`PUT`/`DELETE /cabber/location` | — | 405 | `method_not_allowed` |

Новые коды ошибок не вводятся.

## 5. Состояния

Состояний нет: запись создаётся один раз и больше не меняется. Единственное изменение во времени — добавление новых строк.

## 6. Трассировка к спецификации

| Требование / сценарий | Чем проверяется |
|---|---|
| US1-1, FR-001, FR-006 | Сервис: запись создаётся, `received_at` равен значению инъецированных часов; интеграционный тест репозитория |
| US1-2, FR-005, SC-002 | Интеграционный тест: N вставок → N строк, прежние не изменены; quickstart §5 (`select count(*)`) |
| US1-3, FR-002, SC-003 | Табличные unit-тесты границ ±90/±180, значений за ними, NaN; тест `check`-ограничения на уровне БД |
| US1-4, FR-003 | Тесты разбора тела gateway: пропуск, строка, `null`, не-JSON, лишний размер |
| US1-5, FR-008, SC-004 | Тест роутера: без токена/с неверным токеном `location` не вызывается и ответ 401 — тем же телом, что для `DELETE /cabber/session` |
| US1-6, FR-007 | Тест: две отправки подряд без пауз обе принимаются; нет кода «слишком часто» ни в контракте, ни в коде |
| FR-004 | Проверка числа строк до и после отклонённого запроса |
| FR-009 | Тест: `cabber_id` берётся только из ответа `VerifyCabberSession`; свойство `cabber_id` в теле REST — неизвестное и отклоняется с `400 invalid_request`, в контракте его нет |
| FR-010, SC-005 | Интеграционный тест репозитория (строка видна из другого соединения) и ручная проверка перезапуска контейнера `location-db` (quickstart §5): автоматизировать перезапуск контейнера в тестах репозитория нечем |
| FR-011, SC-006 | Тест-«утечка»: ответы, логи и метрики не содержат пары координат отправленного запроса |
| FR-012 | Тесты контракта: `TestCanonicalContractMatchesRepositoryReference`, `TestRouterPathsAreDefinedInContract`, parity proto; `info.version` 1.2.0 |
| Edge: параллельные запросы | Интеграционный тест с гонкой двух вставок одного каббера: обе строки есть, максимум по `(received_at, id)` определён однозначно |
| Edge: выход не стирает записи | Тест: запись, `DELETE /cabber/session`, повтор записи с прежним токеном — 401, строки остались |
| Edge: избыточная точность | Unit-тест округления до 7 знаков |
