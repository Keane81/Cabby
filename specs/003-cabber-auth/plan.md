# Implementation Plan: Каббер — регистрация, аутентификация и выход (v1)

**Branch**: `003-cabber-auth` | **Date**: 2026-09-24 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/003-cabber-auth/spec.md`

## Summary

Три публичные операции REST (регистрация каббера, вход, выход) принимает `cabby-gateway` и передаёт в `auth` по gRPC. `auth` владеет учётными записями кабберов и сессиями, хранит их в PostgreSQL (база `auth`) за репозиторием, пароли хранит только в формате Argon2id, доступ выдаёт непрозрачным Bearer-токеном, отзываемым на сервере: 96 часов от входа и не более 24 часов бездействия. Сервис назван по домену (аутентификация), а не по субъекту: в v1 он обслуживает только кабберов, но спроектирован так, чтобы к нему могли добавиться пассажиры и администраторы. gRPC-контракт лежит в отдельном модуле `contracts`, общем для всех микросервисов. Спецификация 001 (health-check) и 002 (контракт, модель ошибок, SemVer) сохраняют поведение без изменений: новые операции добавляются в контракт как minor-версия 1.1.0.

## Technical Context

**Language/Version**: Go 1.26.1 (в `go.mod` существующего gateway; локальный тулчейн 1.25.0 добирает 1.26.1 через `GOTOOLCHAIN=auto`)

**Primary Dependencies**:
- `google.golang.org/grpc` + `google.golang.org/protobuf` — межсервисный контракт и сервер/клиент
- `github.com/jackc/pgx/v5` — единственный драйвер PostgreSQL
- `golang.org/x/crypto/argon2` — хеширование паролей
- `github.com/prometheus/client_golang` (v1.24.1, уже есть), `github.com/rs/zerolog` (v1.35.1, уже есть) — без изменений версий
- Codegen: `buf` ставится локально разработчиком (`go install github.com/bufbuild/buf/cmd/buf@latest`), сгенерированный код коммитится

**Storage**: PostgreSQL 18 (`postgres:18-alpine`) в `compose.yaml`, база `auth` и роль `auth` принадлежат сервису `auth`, данные на томе `auth-data`; две таблицы — `cabber`, `cabber_session`. Появляется впервые: в репозитории сейчас нет ни драйвера БД, ни миграций, ни сервиса БД.

**Testing**: стандартный `go test` (как в gateway): `make test`, `make test-race`, `make vet` в каждом модуле. Интеграционные тесты БД — через env-gate по DSN, без testcontainers и без новых зависимостей.

**Target Platform**: Linux-контейнеры в Docker Compose, только локальная сеть compose; из сервисных портов наружу публикуется единственный — HTTP gateway (`127.0.0.1:8082`). Метрики (`:9091` у gateway, `:9094` у `auth`) и gRPC (`:9093`) остаются внутри сети, их смотрит Prometheus по внутреннему адресу; наружу выходят только порты самой наблюдающей системы — Prometheus `127.0.0.1:9090` и Grafana `127.0.0.1:3000`.

**Project Type**: backend-монорепозиторий, микросервисы; три Go-модуля после изменения

**Performance Goals**: ≤ 5 rps суммарно на три операции; p95 отклика входа ≤ 250 мс (основная задержка — хеширование пароля, 20–50 мс при выбранных параметрах); дедлайн вызова `gateway → auth` — 2 с; пул соединения с PostgreSQL — до 8 активных.

**Constraints**: не более 2 одновременных хеширования паролей (ограничение памяти Argon2, см. research R-07); RSS `auth` < 256 MiB; пароли, токены и `email` не попадают в логи, метрики и сообщения об ошибках (проверяется тестами, как в gateway); `/healthz` сохраняет семантику спецификации 001 и не зависит от доступности БД.

**Scale/Scope**: 3 модуля (`cabby-gateway`, `auth`, `contracts`), 2 сервиса в compose + PostgreSQL, 7 пакетов внутренней структуры у нового сервиса (`config`, `service`, `repo`, `migrate`, `password`, `token`, `grpcserver`) и 2 новых пакета у gateway (`authclient`, `requestid`), 3 REST-операции, 3 gRPC-метода, 2 таблицы.

**Structure Decision**: сервис называется `auth`, а не `cabber-auth` и не `cabby-auth`, потому что его роль — аутентификация разных субъектов: в v1 это кабберы, в будущем пассажиры и администраторы (решение пользователя от 2026-09-24). Имя не наследует префикс продукта, как `cabby-gateway`: короткое `auth` читается в адресе внутри сети compose (`auth:9093`) и в имени базы, а `CABBY_AUTH_*` в переменных окружения и `cabby_auth_*` в метриках сохраняют префикс — он уже совпадает с конвенцией gateway (`CABBY_GATEWAY_PORT`, `cabby_gateway_health_checks_total`). Требования v1 при этом остаются кабберскими, и методы контракта тоже (`RegisterCabber`, `CreateCabberSession`) — обобщение не вводится раньше, чем появляется второй субъект. Контракт вынесен в отдельный модуль `contracts`, общий для всех микросервисов: обе стороны генерируют код из одного `.proto` и не держат копии, а потребитель не тащит зависимости изготовителя — при контрактах внутри `auth` в граф gateway попали бы `pgx` и `x/crypto/argon2`. Внутри сервиса слои разделены по ответственности: `grpcserver` (транспорт) → `service` (кейсы и проверки) → `repo` (хранилище), криптография и токены вынесены в `password` и `token`, чтобы зависимость от Argon2 и формата PHC не протекала в кейсы. У gateway намеренно не появляется новая архитектура: новые операции добавляются строками в роутер на `http.ServeMux` и в `internal/server/*`, а gRPC остаётся за портом `Operations` в `internal/authclient`.

## Поведение при отказах и развёртывание

- `auth` недоступен, дедлайн истёк, БД недоступна → `503` с `error.code = service_unavailable`. Ложного успеха нет (edge case спецификации «Отказ хранилища»).
- Невалидные данные → `400 invalid_request` плюс необязательное поле `field`; при нескольких недостатках сообщается первый в фиксированном порядке `name → email → password`.
- Занятый email → `409 email_taken`, без атрибутов существующей записи.
- Неверные учётные данные, отсутствующий, отозванный или истёкший токен → единый `401 unauthorized`.
- Неизвестный путь или метод → поведение из 002 без изменений (`404 unknown_operation`, `405 method_not_allowed`). Обращение к отсутствующим операциям смены и восстановления пароля даёт `404` — это проверяемый FR-026.
- Порядок развёртывания: (1) `contracts`, (2) PostgreSQL и `auth` (миграция 0001, трафик снаружи нулевой), (3) `cabby-gateway` с контрактом 1.1.0, (4) дашборды. Откат — вернуть gateway на 1.0.0: новые пути становятся `unknown_operation`, сервис и схема остаются без изменений. Оба шага аддитивны, поэтому SC-008 выполняется без миграции данных.
- Миграция 0001 выполняется при старте сервиса под advisory lock с ограниченной паузой на ожидание PostgreSQL; повторный запуск безопасен.

## Complexity Tracking

> Заполнено, потому что принципы III и IV требуют оправдания отступлений.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Нет распределённой трассировки (принцип III требует её через границы сервисов) | Первый межсервисный вызов в проекте; OTel-collector, Jaeger и их инфраструктура — это два новых сервиса в compose и десятки зависимостей ради трёх операций, у которых задержка и так измеряется гистограммой | Полная трассировка через OTel: отклонена из-за объёма «простой первой версии» и необходимости внешнего хранилища следов. Частичная замена реализована (T085): `request_id` из 8 байт `crypto/rand` (16 hex) генерируется на входе gateway, логируется обеими сторонами и передаётся в gRPC-metadata под ключом `x-request-id`; сервис переиспользует только значение правильной формы, иначе берёт своё. Плюс метрика задержки вызова — вместе это покрывает 90% инцидентов. Пересмотр: при добавлении второго межсервисного вызова или бизнес-операций каббера |
| Право субъекта на удаление данных не реализовано (часть принципа IV) | Дерегистрация и восстановление пароля вне объёма спецификации по решению пользователя; `Dependencies` уже помечает это блокирующим долгом перед запуском на реальных водителях | Сделать удаление в этом же объёме: отклонено пользователем явно (правка объёма 2026-09-24). Ограничение зафиксировано как FR-028 и долг, а не как принятый риск |
| Отдельный модуль контрактов (`contracts`) | Оба сервиса компилируют код из одного `.proto`, и модуль заранее готов принять контракты следующих сервисов; дублирование `.proto` или кода между модулями расходилось бы незаметно, а внешнего реестра артефактов нет | Контракты внутри модуля `auth`: отклонено, тогда gateway зависит от модуля с `pgx` и `argon2` и перекомпилирует чужую логику; копия `proto` у gateway — источник расхождений |
| Слой репозитория (`internal/repo`) вместо прямых запросов из кейсов | Требование пользователя разделять слой БД; кейсы остаются тестируемыми без PostgreSQL, а pgx и SQL не протекают в `service` | Прямые вызовы `pgxpool.Query` из кейсов: отклонено, тогда каждый кейс требовал бы живую БД для проверки |
| Собственный раннер миграций вместо `golang-migrate`/`Atlas` | `go:embed migrations/*.sql` + версионная таблица + advisory lock — около ста строк, никаких новых бинарников и зависимостей в модуле | Внешняя CLI-утилита: отклонена, потому что требует установки на каждую машину и в CI, которого в репозитории пока нет |
