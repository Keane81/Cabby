# Phase 0 Research: Каббер — регистрация, аутентификация и выход (v1)

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-24

Решения, закрывающие области, которые спецификация намеренно оставила этапу планирования (см. Assumptions), и решения, без которых нельзя построить сервис `auth`. Отклонённые альтернативы перечислены для каждого пункта.

## R-01. Протокол между gateway и auth — gRPC

**Decision**: `auth.v1.AuthService` по HTTP/2, контракт в `backend/contracts/proto/auth/v1/auth.proto`, сгенерированный код коммитится в `contracts/authpb/`. Оба модуля подключают `contracts` через `replace` на локальный путь.

**Rationale**: Требование пользователя. Дополнительно: контракт с известными методами и типами устраняет риск «роутер и контракт разошлись», который в gateway сейчас закрывается регуляркой по тексту YAML; межсервисные ошибки становятся категоризованными (`INVALID_ARGUMENT`, `UNAUTHENTICATED`, `ALREADY_EXISTS`, `UNAVAILABLE`), что ровно соответствует модели ошибок из спецификации 002.

**Alternatives rejected**: JSON поверх HTTP — проще, но требование пользователя явно про gRPC; общий Go-пакет с интерфейсом — не является сетевым контрактом и не переживёт появление второго потребителя.

## R-02. Где живёт контракт и как не разойтись без реестра артефактов

**Decision**: отдельный Go-модуль `contracts` — единственный источник `.proto` и сгенерированного кода для всех микросервисов монорепозитория; контракт аутентификации лежит в `backend/contracts/proto/auth/v1/auth.proto`, код — в `backend/contracts/authpb`. Владелец конкретного пакета контракта — сервис, который его публикует (`auth.v1` принадлежит `auth`); gateway — только потребитель. Каноническая копия `.proto` — в `contracts`, эталонная — в `specs/003-cabber-auth/contracts/auth.proto`, равенство байтов проверяет тест в `contracts`.

**Rationale**: Приватного реестра Go-модулей в проекте нет, публикуемых версий тоже. `replace` на относительный путь — единственный способ иметь одну генерацию на два модуля. Вынос контрактов в отдельный модуль, а не в каталог сервиса нужен, чтобы потребитель не зависел от внутренности изготовителя: при контрактах внутри `auth` импорт `authpb` затянул бы в граф зависимостей gateway `pgx`, `x/crypto/argon2` и внутренние пакеты кейсов. Правило «две байт-в-байт копии плюс тест» уже работает для REST-контракта (`TestCanonicalContractMatchesRepositoryReference`) и переносится один в один.

**Alternatives rejected**: дублирование `.proto` в обоих модулях — расхождение обнаруживается только на несостыковке типов при сборке; контракты внутри модуля `auth` — экономит один модуль, но обязывает потребителя тянуть зависимости изготовителя; `go.work` — игнорируется корневой `.gitignore` и потому не воспроизводится у других разработчиков; один модуль на всё — нарушает принцип I, смешивая владение данными и транспорт.

## R-03. Форма публичного REST-интерфейса

**Decision**:
- `POST /cabbers` — регистрация: `{name, email, password}` → `201 {cabber_id, email}`
- `POST /cabber/session` — создание сессии (вход): `{email, password}` → `201 {access_token, expires_at}`
- `DELETE /cabber/session` — удаление сессии (выход): заголовок `Authorization: Bearer <token>` → `204`

**Rationale**: Соответствие согласованному решению FR-010: регистрация доступ не выдаёт, поэтому вход — отдельный создаваемый ресурс. `expires_at` в ответе входа обязателен, иначе клиент не может подготовиться к обязательному повторному входу (FR-013). Имя пути во множественном числе для коллекции и единственном для подчинённого singleton-ресурса — конвенция из уже существующих ответов (`/healthz`, `/openapi.yaml` новых соглашений не задают).

**Alternatives rejected**: `/auth/register`, `/auth/login`, `/auth/logout` — глагольные RPC-подобные пути против REST-подхода, заявленного пользователем; `/cabber` в единственном числе для регистрации — теряет связь с коллекцией создаваемых ресурсов.

**Consequence**: путь `/cabbers/session` вместо `/cabber/session` не выбран намеренно: сессия не принадлежит «единственному текущему» кабберу в URI, владелец вычисляется по токену на сервере (FR-015), поэтому URI не участвует в авторизации.

## R-04. Схема доступа: непрозрачный Bearer-токен с серверным состоянием

**Decision**: 256 бит из `crypto/rand`, base64url без знаков выравнивания; в БД хранится только SHA-256 хеш предъявленного значения (`token_hash bytea unique`). Проверка: поиск по хешу, затем разбор состояния (`revoked_at`, `expires_at`, `last_seen_at`). Дополнительных секретов в токене нет, из его значения состояние не вычисляется.

**Rationale**: FR-020 и FR-021 требуют отзыва доступа — это возможно только при проверяемом на сервере состоянии (решение пользователя о серверных сессиях). Хранение хеша вместо значения делает дамп таблицы `cabber_session` бесполезным для атаки. Отсутствие подписи и структуры снимает целый класс отказов (ключи подписи, протухание часов, ротация).

**Alternatives rejected**: JWT со stateless-подписью — не даёт отзыва без реестра отозванных, то есть всё равно требует БД; cookie-схема — навязывает браузерную модель и CSRF-защиту, а потребители — мобильные приложения; PKCE/OIDC — многократно сложнее требуемого.

## R-05. Хранилище — PostgreSQL

**Decision**: `postgres:18-alpine` в `compose.yaml`, отдельная база `auth` с ролью `auth` (принадлежат сервису аутентификации; внутри неё таблицы `cabber` и `cabber_session` — v1 хранит только регистрацию кабберов), данные — на именованном томе `auth-data`, доступ только по внутренней сети compose, порт наружу не публикуется. Драйвер — `github.com/jackc/pgx/v5` (`pgxpool`). Уникальность `email` обеспечивает обычный unique-индекс по канонизированному значению: приведение к нижнему регистру выполняется приложением, а не оператором `citext` или функциональным индексом.

**Rationale**: В репозитории нет ни одной работы с БД, поэтому выбор ничем не ограничен; PostgreSQL уже выбран как общая инфраструктура проекта. Уникальность и срок жизни проще обеспечить ограничениями БД, чем приложением (FR-003, FR-009). `on delete cascade` для сессий оставлен на будущее: в v1 кабберов не удаляют.

**Alternatives rejected**: SQLite — не выдержит запуска вне локального тома и создаст вторую схему развёртывания; in-memory реестр сессий — теряет доступы при рестарте и не масштабируется между репликами; внешний кэш с TTL (Redis) — вторая система там, где достаточно одной.

## R-06. Миграции — встроенный раннер на `go:embed`

**Decision**: каталог `backend/auth/migrations/` с парами `NNNN_name.up.sql` / `.down.sql`; таблица `schema_migration(version, applied_at)`; применение в транзакции под `pg_advisory_lock`; вызов при старте сервиса с ограниченной паузой на ожидание PostgreSQL (30 попыток по 1 с). Флаг `-migrate` применяет миграции и выходит — этим же кодом пользуется `make -C backend/auth migrate`.

**Rationale**: Никаких новых бинарников и зависимостей; миграция становится частью жизненного цикла контейнера, а compose-старт не требует ручного шага. Advisory lock делает повторный запуск идемпотентным.

**Alternatives rejected**: `golang-migrate` или Atlas — требуют CLI на каждой машине и в будущем в CI, которого в репозитории нет; авто-создание схемы из кода (`CREATE TABLE IF NOT EXISTS`) — неуправляемая эволюция схемы.

## R-07. Хеш пароля — Argon2id и его параметры

**Decision**: `golang.org/x/crypto/argon2`, argon2id, `time=2`, `memory=19 MiB`, `threads=1`, `keyLen=32`, `salt=16` байт `crypto/rand`; формат хранения — PHC-строка `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`. Параллельность хеширования ограничена семафором на 2 одновременных вычисления. Параметры — значение по умолчанию пакета `password`, в тестах подменяются структурой `Params` с малыми значениями.

**Rationale**: Требование пользователя (argon2). Выбранные значения — нижняя граница рекомендаций OWASP для argon2id, а не верхняя: задержка хеширования 20–50 мс и 19 MiB на вычисление укладываются в бюджет v1 (RSS < 256 MiB, ≤ 5 rps), тогда как «эталонные» 64 MiB × 3 прохода дали бы ~300 мс и риск выхода за лимит памяти при двух одновременных регистрациях. PHC-строка хранит алгоритм и параметры, что даёт путь к ротации хешей без миграции данных.

**Alternatives rejected**: bcrypt — проще, но ограничен 72 байтами пароля и хуже переносит рост железа; scrypt — тоже приемлем, но беднее по настройкам; готовая библиотека формата PHC — лишняя зависимость ради 40 строк кода.

## R-08. Верхние пределы длины полей

**Decision**: `name` — от 1 до 64 символов, `email` — не более 254 символов, `password` — от 4 до 16 символов. Считаются символы Юникода, а не байты. Границы записаны во FR-006, нижняя граница пароля и минимальный формат email — там же (FR-006, FR-007).

**Rationale**: Нужен отказ от неограниченного ввода: длина пароля уходит в Argon2, длина `name` и `email` — в индексы и логи. Верхняя граница пароля в 16 символов — решение пользователя от 2026-09-24: она ограничивает и стоимость проверки, и размер поля. Следствие принято осознанно: passphrase длиннее 16 символов отклоняется как невалидный ввод, отдельных подсказок о причине нет (FR-006). 254 символа для `email` — практический предел адреса из RFC 5321.

**Alternatives rejected**: «без верхнего предела» — неприемлемо, так как оставляет неограниченное потребление памяти; «256 символов, как в первоначальном плане» — отклонено пользователем в пользу короткого пароля; предел в 72 байта как у bcrypt — тихая потеря части пароля.

## R-09. Таймауты, повторные попытки и готовность

**Decision**: дедлайн одного вызова `gateway → auth` — 2 с, повторных попыток нет. Пул PostgreSQL — до 8 соединений, ожидание свободного — 1 с, затем `UNAVAILABLE`. `/healthz` остаётся независимым от БД и от `auth` (семантика спецификации 001 не меняется). Деградация: недоступность зависимостей даёт `503 service_unavailable` на трёх новых операциях.

**Rationale**: Требование принципа III (таймауты и ограниченные попытки) выполняется через «ограничено = один раз»: `RegisterCabber` и `CreateCabberSession` не идемпотентны, и автоматический повтор мог бы создать вторую учётную запись или вторую сессию либо замаскировать атаку перебором под медленный ответ. Идемпотентность есть у `DeleteCabberSession`, но и она повторяется один раз, чтобы не вводить два разных правила.

**Alternatives rejected**: повтор с экспоненциальной задержкой — стандартен для идемпотентных операций, здесь увеличивает хвост задержки входа и требует различать «повторить» и «не создавать дубль»; health-check с проверкой БД — изменил бы поведение 001 и нагнетал бы фоновый трафик, против которого уже есть решение в quickstart 001.

## R-10. Отзыв доступа и скользящий срок

**Decision**: `expires_at = created_at + 96h` — абсолютный предел; бездействие ограничено `last_seen_at + 24h`, при этом `last_seen_at` обновляется только если предыдущее значение старше 60 секунд. Часы во все кейсы передаются инъекцией (`service.Now`), тесты используют подставное время. Устаревшие строки чистит фоновый тикер раз в час (условия: истёкший абсолютный срок или отзыв — старше 7 дней).

**Rationale**: FR-013 требует обоих ограничений: 96 часов абсолютного срока и 24 часов бездействия — значения решения пользователя от 2026-09-24. Запись раз в минуту на активную сессию ограничивает число записи БД (~1 на минуту на каббера вместо 1 на запрос), не ломая семантику idle-таймаута: погрешность ≤ 60 с.

**Alternatives rejected**: только абсолютный срок — не выполняет FR-013 про бездействие; скользящий срок без абсолютного предела — позволяет токеновой краже жить неограниченно; бездействие 96 часов вместе с абсолютным сроком — отклонено пользователем: неактивный доступ должен прекращаться за сутки; отдельный кэш сессий — второй источник истины.

## R-11. Наблюдаемость трёх операций на двух сервисах

**Decision**:
- `cabby-gateway`: `cabby_gateway_cabber_requests_total{operation,outcome}` и `cabby_gateway_cabber_dependency_duration_seconds{operation}` (гистограмма), где `operation ∈ {register, create_session, delete_session}`, `outcome ∈ {success, rejected, unauthorized, unavailable, failure}` — значения фиксированы и не содержат персональных данных.
- `auth`: `cabby_auth_requests_total{method,outcome}` и `cabby_auth_request_duration_seconds{method}`, плюс `cabby_auth_repository_query_total{query,outcome}`.
- Гистограммы задержки на обеих сторонах используют один и тот же набор границ: `{0.05, 0.1, 0.25, 0.5, 1, 2.5}` с — нижняя граница совпадает с ожидаемой задержкой хеширования, `0.25` — целевой p95 входа (R-07, Performance Goals), `2.5` накрывает дедлайн вызова в 2 с (R-09), поэтому правый «хвост» всегда различим.
- Логи: `zerolog` в тех же полях, что и в gateway (`operation`, `error_class`), добавляется `request_id`. `email` не логируется даже в маске; токен и пароль не логируются никогда.
- Идентификатор запроса: `request_id` создаётся на входе gateway — 16 шестнадцатеричных символов из 8 байт `crypto/rand`, кладётся в `context` запроса и в каждую строку лога обеих сторон. Через границу сервисов он передаётся в gRPC-metadata под ключом `x-request-id`; значение этого ключа зафиксировано константой в обоих модулях (`backend/cabby-gateway/internal/requestid`, `backend/auth/internal/grpcserver`). Сервис переиспользует только значение правильной формы — 16 символов `[0-9a-f]`, иначе генерирует своё, чтобы внешний вызов не мог подставить в чужой лог произвольный текст. gateway генерирует идентификатор до валидации тела, поэтому отказ `400` тоже остаётся ищущимся.
- Дашборд `deploy/monitoring/grafana/dashboards/auth.json` с тем же подходом к отражению недоступности (`up`) из дашборда 001; scrape-джоб Prometheus `auth` на порт метрик 9094 внутри сети compose. Порт метрик, как и `:9091` в gateway, — константа кода, а не переменная окружения: наружу он не публикуется, а расхождение с `target` в `deploy/monitoring/prometheus.yml` означает просто пустой дашборд.

**Rationale**: Требование пользователя (REST и gRPC на дашбордах) и принципа III. Разделение метрик по двум сервисам нужно, чтобы на дашборде было видно, где именно теряется задержка: HTTP-слой gateway, gRPC-вызов или БД.

**Alternatives rejected**: единый дашборд с gateway-панелями — смешивает разные владельцев; экспорт стандартных сборщиков Go — осознанно отложен, текущий registry gateway их тоже не содержит, и добавление в одном сервисе создало бы несимметрию дашбордов.
