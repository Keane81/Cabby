# Research: Веб-просмотрщик БД

## R-01. Как «из веб-интерфейса напрямую в БД»
- **Decision**: браузер → тонкий Go-процесс `dbviewer` → PostgreSQL. Gateway и сервисы не участвуют.
- **Rationale**: браузер не может открыть соединение с PostgreSQL; серверный слой нужен, чтобы держать DSN вне браузера, соблюдать read-only и маскировать секреты.
- **Alternatives**: PostgREST/Hasura (поверх БД, но секреты и лимиты настраиваются хуже, лишний компонент); Adminer/pgAdmin (разрешают запись, показывают хэши); эндпоинты в gateway (прямо исключено пользователем).

## R-02. Стек
- **Decision**: Go + pgx + `embed` со статикой; фронтенд на ванильном JS без сборки.
- **Rationale**: Go и pgx уже в проекте; нет Node-цепочки; один образ `scratch` как у остальных сервисов.
- **Alternatives**: React/Vite — оправдано лишь при росте UI, добавляет сборку и зависимости.

## R-03. Интроспекция схемы
- **Decision**: читать `pg_catalog`/`information_schema` при старте и по кнопке «обновить» (кэш с TTL 30 с): таблицы схемы `public`, столбцы, типы, первичный ключ.
- **Rationale**: FR и Edge Case про изменение схемы; идентификаторы в SQL подставляются только из этого набора (через `pgx.Identifier.Sanitize`), что исключает инъекцию через имена.
- **Alternatives**: захардкодить три таблицы — ломается при новой миграции.

## R-04. Классификация столбцов
- **Decision**: столбец *sensitive*, если имя содержит `hash|secret|token|password` либо тип `bytea`; sensitive значения никогда не читаются из БД (в SELECT подставляется константа-маркер), не участвуют в поиске/фильтрах/сортировке. Поиск — по столбцам типов `text`, `varchar`, `uuid` (через `::text`), кроме sensitive. Фильтры — по типам: текст (равно/содержит), число, `timestamptz` (диапазон), `uuid` (равно), `bool`.
- **Rationale**: «по умолчанию безопасно» для будущих столбцов (edge case); значение не покидает БД, значит не попадёт ни в ответ, ни в лог.
- **Alternatives**: allowlist — надёжнее, но требует правки кода при каждом новом столбце; выбран denylist по шаблону + bytea как баланс (явное решение, пересматриваемое при росте схемы).

## R-05. Read-only и лимиты
- **Decision**: каждый запрос в транзакции `READ ONLY` с `SET LOCAL statement_timeout = '5s'`; пул ≤ 4 соединений на базу; размер страницы 1–200 (по умолчанию 50); офсетная пагинация со стабильной сортировкой «выбранный столбец, затем первичный ключ».
- **Rationale**: PostgreSQL сам отвергает записи в read-only транзакции; таймаут защищает основные БД. Роль БД остаётся владельцем (отдельной роли нет — создание ролей в init-скриптах не срабатывает на уже существующем томе), риск закрыт транзакционным режимом и тестом «запись отвергается».
- **Alternatives**: отдельная read-only роль — лучше по изоляции, но требует миграции для существующих томов; вынесено как возможное усиление.

## R-06. Подсчёт строк на больших таблицах
- **Decision**: без условий — `pg_class.reltuples` (пометка «≈»), если оценка > 100 000, иначе `count(*)`; с условиями — `count(*)` над подзапросом с `LIMIT 10001`, при достижении предела показывается «>10 000».
- **Rationale**: точный `count(*)` на миллионах строк не укладывается в SC-002/SC-003; пользователю нужна ориентировка, а не точное число (FR-003 допускает примерное).
- **Alternatives**: всегда точный count — медленно; keyset-пагинация — не совмещается с произвольной сортировкой и переходом на страницу N.

## R-07. Размеры на диске
- **Decision**: база — `pg_database_size(current_database())`; таблица — `pg_relation_size` (данные, включая TOAST отдельно не показываем), `pg_indexes_size`, `pg_total_relation_size`. Показ в КБ/МБ/ГБ (двоичные), время обновления.
- **Rationale**: «примерно» — то, что считает сам PostgreSQL; SC-004 проверяется той же функцией независимо в тесте.
- **Alternatives**: размер тома docker — недоступен из контейнера и включает WAL/служебное.

## R-08. Сеть и запуск
- **Decision**: сервис `dbviewer` в `compose`, `ports: 127.0.0.1:${CABBY_DBVIEWER_HTTP_PORT:-8090}:8090`, `depends_on` обе БД; DSN — через `env_file ./backend/dbviewer/.env`; БД остаются без публикации портов.
- **Rationale**: FR-016, FR-018; повторяет подход остальных сервисов.
- **Alternatives**: публиковать порты БД на хост — расширяет поверхность атаки.

## R-09. Логирование
- **Decision**: одна строка на запрос: `operation` (list_tables, rows, row, sizes), `table`, `duration_ms`, `error_class`, `request_id`; без значений, поиска, фильтров.
- **Rationale**: FR-019 и правила AGENTS.
