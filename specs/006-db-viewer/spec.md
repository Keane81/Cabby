# Feature Specification: Веб-просмотрщик баз данных auth и location

**Feature Branch**: `feature/hl_beginning`

**Created**: 2026-10-03

**Status**: Draft

**Input**: User description: "Это будет спецификация 006. Хочу получить вэб интерфейс viewer для моих баз данных auth и location с операциями поиска, сортировки, фильтрации. Так же хочу видеть, сколько примерно занимается каждая база данных на диске. Походы в базу данных можно делать напрямую из web-интерфейса минуя gateway"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр таблиц обеих баз (Priority: P1)

Разработчик открывает веб-интерфейс и видит две базы — auth и location. Для каждой доступен список таблиц с примерным числом строк. Выбрав таблицу, он видит её содержимое постранично: названия столбцов, значения, общее число строк. Таблицы с большим числом строк (например, миллионы координат после нагрузочного прогона эмулятора) открываются без зависания, потому что данные подгружаются страницами.

**Why this priority**: Без возможности просто увидеть данные остальные операции бессмысленны. Этот срез уже даёт ценность: заглянуть в базу, не открывая консоль.

**Independent Test**: Открыть интерфейс на локальном стеке с данными, выбрать каждую таблицу каждой базы и пролистать первые страницы; убедиться, что данные совпадают с содержимым базы, а большие таблицы открываются быстро.

**Acceptance Scenarios**:

1. **Given** локальный стек запущен, **When** разработчик открывает интерфейс, **Then** он видит базы auth и location и список таблиц каждой.
2. **Given** выбрана таблица, **When** она открывается, **Then** показываются заголовки столбцов и первая страница строк, а также общее (или примерное, если таблица очень большая) число строк.
3. **Given** таблица содержит больше строк, чем помещается на странице, **When** разработчик переходит на следующую или предыдущую страницу, **Then** показываются соответствующие строки без повторов и пропусков.
4. **Given** таблица пуста, **When** она открывается, **Then** показывается явное сообщение «нет данных», а не пустой экран.
5. **Given** одна из баз недоступна, **When** открывается интерфейс, **Then** недоступная база помечена ошибкой с понятным текстом, а вторая остаётся доступной.

### User Story 2 - Поиск, фильтрация и сортировка (Priority: P1)

Разработчик находит нужные записи: вводит строку в поиск (например, часть email каббера или идентификатор), накладывает фильтры по столбцам (диапазон дат создания, статус сессии «активна/отозвана/истекла», идентификатор каббера, диапазон координат) и сортирует таблицу по любому столбцу по возрастанию или убыванию. Поиск, фильтры и сортировка комбинируются и применяются ко всей таблице, а не только к показанной странице.

**Why this priority**: Это прямо названные в запросе операции и основная причина существования просмотрщика: быстро найти конкретные записи среди большого объёма.

**Independent Test**: На базе с заведомо известными данными найти каббера по части email, отфильтровать координаты одного каббера за интервал времени и отсортировать по времени получения по убыванию; результаты должны совпадать с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** открыта таблица, **When** разработчик вводит строку поиска, **Then** остаются только строки, где совпадение есть хотя бы в одном текстовом столбце, подходящем для поиска, а число найденных строк отображается.
2. **Given** открыта таблица, **When** разработчик задаёт фильтры по нескольким столбцам, **Then** показываются только строки, удовлетворяющие всем фильтрам одновременно.
3. **Given** открыта таблица, **When** разработчик выбирает сортировку по столбцу, **Then** строки упорядочиваются по этому столбцу по всей таблице, а не только внутри страницы; повторный выбор меняет направление.
4. **Given** заданы поиск, фильтры и сортировка, **When** разработчик переходит между страницами, **Then** они сохраняются, а при смене таблицы — сбрасываются.
5. **Given** условия ничего не находят, **When** результат пуст, **Then** показывается сообщение «ничего не найдено» и возможность сбросить условия.
6. **Given** значение фильтра некорректно (например, нечисловое там, где нужно число), **When** оно применяется, **Then** разработчик видит понятную подсказку, а таблица не ломается.

### User Story 3 - Размер каждой базы на диске (Priority: P2)

Разработчик видит на главном экране, сколько примерно места занимает каждая база данных на диске, а при выборе базы — размер каждой её таблицы (с индексами). Размеры показываются в человекочитаемых единицах (КБ, МБ, ГБ) и обновляются по запросу, чтобы можно было наблюдать рост базы во время нагрузочного прогона.

**Why this priority**: Явно запрошено, но не мешает просмотру данных; полезно для оценки объёма, который создаёт эмулятор.

**Independent Test**: Запомнить показанный размер базы location, выполнить прогон эмулятора, нажать «обновить» и убедиться, что размер вырос и сопоставим с независимой оценкой размера той же базы средствами самой базы данных.

**Acceptance Scenarios**:

1. **Given** открыт главный экран, **When** загрузились данные, **Then** для каждой базы показан её примерный размер на диске.
2. **Given** выбрана база, **When** открывается её страница, **Then** виден размер каждой таблицы, отдельно данные и индексы (или суммарно), с сортировкой по размеру.
3. **Given** данные в базе изменились, **When** разработчик нажимает «обновить», **Then** размеры пересчитываются и показывается время последнего обновления.

---

### User Story 4 - Просмотр отдельной записи и безопасное отображение секретов (Priority: P3)

Разработчик открывает отдельную запись и видит все её поля целиком (длинные значения не обрезаны), может скопировать значение. Хэши паролей и хэши токенов сессий по умолчанию не показываются: вместо них стоит пометка о скрытом значении.

**Why this priority**: Удобство и гигиена данных; основные сценарии работают и без неё, но защита секретов — требование конституции.

**Independent Test**: Открыть запись каббера и запись сессии; убедиться, что поля хэшей скрыты, а остальные поля видны полностью.

**Acceptance Scenarios**:

1. **Given** открыта таблица, **When** разработчик выбирает строку, **Then** показываются все поля записи полностью.
2. **Given** в таблице есть столбцы с хэшами паролей или токенов, **When** они отображаются в списке или в карточке записи, **Then** их значения скрыты, а поиск, фильтры и сортировка по ним недоступны.

---

### Edge Cases

- Очень большая таблица (миллионы строк после прогона эмулятора на 50 000 кабберов): страница открывается, поиск и сортировка завершаются за разумное время либо разработчик получает понятное сообщение, что запрос слишком тяжёлый, а не зависший интерфейс.
- Запрос выполняется слишком долго: он прерывается по предельному времени, и показывается сообщение с предложением сузить условия.
- Данные меняются во время просмотра (эмулятор пишет координаты): пагинация не должна падать; допустимо, что между страницами набор строк слегка сдвигается.
- Значения со спецсимволами, очень длинные строки, пустые значения (`NULL`): отображаются корректно, `NULL` визуально отличается от пустой строки.
- Попытка внедрения произвольных условий через поле поиска или фильтра (в том числе служебные символы): значения всегда трактуются как данные, а не как часть запроса.
- Сетевое время жизни: обе базы доступны только на локальном стеке; интерфейс недоступен из внешней сети.
- Схема базы изменилась (появилась новая таблица или столбец): интерфейс показывает актуальную схему без ручной перенастройки; новые чувствительные столбцы по умолчанию не должны раскрываться, пока их не пометят безопасными.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять веб-интерфейс, в котором доступны базы auth и location.
- **FR-002**: Система MUST показывать для каждой базы список её таблиц с примерным числом строк.
- **FR-003**: Система MUST показывать содержимое выбранной таблицы постранично с настраиваемым размером страницы и общим числом строк (точным, а для очень больших таблиц — примерным с пометкой).
- **FR-004**: Пользователь MUST иметь возможность искать по строке во всех текстовых столбцах таблицы, пригодных для поиска.
- **FR-005**: Пользователь MUST иметь возможность фильтровать строки по значениям отдельных столбцов (точное значение, диапазон для чисел и дат, булев признак) с комбинированием нескольких фильтров по условию «И».
- **FR-006**: Пользователь MUST иметь возможность сортировать строки по любому столбцу в обоих направлениях; сортировка, поиск и фильтры применяются ко всей таблице.
- **FR-007**: Система MUST сохранять поиск, фильтры, сортировку и размер страницы при переходе между страницами и сбрасывать их при смене таблицы.
- **FR-008**: Система MUST показывать для каждой базы примерный размер на диске, а для каждой таблицы — размер данных и индексов, в человекочитаемых единицах, с возможностью обновления по запросу.
- **FR-009**: Система MUST работать только на чтение: никакая операция интерфейса не изменяет, не добавляет и не удаляет данные и не меняет схему.
- **FR-010**: Система MUST скрывать значения чувствительных столбцов (хэши паролей, хэши токенов сессий) во всех представлениях и исключать их из поиска, фильтров и сортировки.
- **FR-011**: Значения поиска и фильтров MUST всегда интерпретироваться как данные; пользовательский ввод не может изменить смысл или структуру запроса к базе.
- **FR-012**: Система MUST ограничивать время выполнения каждого запроса и размер возвращаемой страницы и сообщать пользователю понятной ошибкой, если лимит превышен.
- **FR-013**: Система MUST различать и показывать `NULL`, пустые значения и длинные значения (с возможностью развернуть целиком).
- **FR-014**: Система MUST корректно показывать ошибки недоступности базы отдельно по каждой базе, не блокируя работу с другой.
- **FR-015**: Пользователь MUST иметь возможность открыть отдельную запись и увидеть все её поля целиком.
- **FR-016**: Интерфейс MUST быть доступен только с локальной машины разработчика; во внешнюю сеть он не публикуется.
- **FR-017**: Просмотрщик MUST работать независимо от gateway и остальных сервисов: недоступность gateway не влияет на его работу, а его работа не создаёт нагрузки на gateway.
- **FR-018**: Просмотрщик MUST запускаться вместе с локальным стеком одной командой и не требовать ручной настройки подключения к базам в типовом случае.
- **FR-019**: Просмотрщик MUST не логировать значения данных из баз и пользовательские условия поиска; в диагностике допускаются только операция, таблица, длительность и класс ошибки.

### Key Entities

- **База данных**: именованное хранилище одного сервиса (auth или location); атрибуты — имя, доступность, примерный размер на диске, список таблиц.
- **Таблица**: набор записей одной базы; атрибуты — имя, столбцы, примерное число строк, размер данных и индексов.
- **Столбец**: имя, тип значения (текст, число, дата и время, идентификатор, булев), признаки «чувствителен», «доступен для поиска», «доступен для сортировки и фильтрации».
- **Запись**: одна строка таблицы; набор значений по столбцам.
- **Условия выборки**: сочетание строки поиска, фильтров, сортировки, номера и размера страницы.
- **Сведения о размере**: размер базы и таблиц на диске в байтах и в человекочитаемом виде, момент последнего обновления.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Разработчик находит нужную запись (по части email каббера или по идентификатору) в обеих базах не более чем за 30 секунд с момента открытия интерфейса.
- **SC-002**: Первая страница любой таблицы открывается не дольше чем за 2 секунды на базе, содержащей до 1 млн строк в таблице.
- **SC-003**: Поиск, фильтрация и сортировка по таблице до 1 млн строк возвращают результат не дольше чем за 5 секунд; при превышении лимита пользователь получает понятное сообщение, а не зависший экран.
- **SC-004**: Показанный размер каждой базы отличается от независимой оценки размера средствами самой базы не более чем на 5% на момент обновления.
- **SC-005**: Нет ни одного представления интерфейса, в котором видны хэши паролей или токенов сессий (проверяется просмотром всех таблиц и карточек записей).
- **SC-006**: После любых действий в интерфейсе содержимое баз остаётся неизменным (проверяется сравнением состояния до и после контрольного сценария).
- **SC-007**: Интерфейс запускается вместе с локальным стеком одной командой, и разработчик видит данные обеих баз без дополнительной настройки.
- **SC-008**: Выход из строя gateway не мешает просмотру данных: все сценарии интерфейса выполняются при остановленном gateway.

## Assumptions

- Пользователь один — разработчик проекта; роли и учётные записи для самого просмотрщика не вводятся. Защита обеспечивается тем, что интерфейс доступен только на локальной машине (FR-016).
- Просмотрщик — инструмент разработки и локальной диагностики, а не продуктовая функция; в продуктивной среде он не разворачивается.
- Отступление от принципа I конституции (доступ к хранилищу сервисов минуя их контракты) принято осознанно по прямому требованию владельца проекта. Риск ограничивается режимом «только чтение», скрытием секретов и локальной доступностью; пересмотр — при появлении общего (не локального) окружения, где просмотрщик не должен разворачиваться без отдельного решения.
- Редактирование, удаление и произвольные SQL-запросы вне области: возможен только просмотр с поиском, фильтрацией и сортировкой.
- Просматриваются только таблицы баз auth и location, существующие в текущих миграциях; новые базы подключаются отдельной доработкой.
- Размер на диске — примерная оценка (данные таблиц, индексы и служебные структуры), а не точное значение файловой системы.
- Числа строк для очень больших таблиц могут быть примерными; интерфейс помечает такие значения.
- Мобильная адаптация и многоязычность вне области; интерфейс на русском языке достаточен.
- Экспорт данных, сохранение пресетов фильтров и история запросов вне области первой версии.
- Зависимости: работающий локальный стек с базами auth и location; в проекте пока нет web-клиента, поэтому интерфейс создаётся как новая часть монорепозитория (`web`) с указанием необходимых проверок в плане.
