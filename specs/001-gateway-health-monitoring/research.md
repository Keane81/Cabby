# Research: cabby-gateway health-check и RPS

## 1. Исполнение сервиса

**Decision**: Использовать Go 1.26.1, стандартный `net/http` и `github.com/rs/zerolog` для структурированных JSON-логов; контейнер собирать многоэтапно, запускать как непривилегированный пользователь. Версию Go закрепить как 1.26.1 в модуле и образе сборки. Создавать явный экземпляр `zerolog.Logger` и передавать его обработчику вместо изменения глобального логгера.

**Rationale**: Пользователь указал точную версию Go и выбрал zerolog для логирования. Для одного публичного метода отдельный веб-фреймворк не нужен. Zerolog выводит структурированные JSON-события с уровнем и временем; явная передача логгера упрощает проверку ошибок и безопасную работу нескольких обработчиков.

**Alternatives considered**: `log/slog` был первоначальным выбором, но заменён по указанию пользователя; веб-фреймворк добавляет зависимость без пользы для единственной команды; нестабильный тег образа усложняет воспроизводимость.

**Sources**: [Go releases](https://go.dev/dl/), [net/http](https://pkg.go.dev/net/http), [zerolog](https://github.com/rs/zerolog).

**Risk**: После Go 1.26.1 выходили исправления безопасности. Точная версия сохранена по прямому указанию пользователя; перед выпуском нужна проверка применимости опубликованных исправлений и отдельное решение об обновлении. [Go release history](https://go.dev/doc/devel/release).

## 2. Контракт команды

**Decision**: Публичная команда — `GET /healthz` на порту `CABBY_GATEWAY_PORT` (8080 без переменной; локальный пример 8082 в `backend/cabby-gateway/.env.example`). Успех — HTTP 200 и короткий JSON `{"status":"ok"}`; после снятия готовности при корректной остановке запрос, успевший достичь обработчика, получает HTTP 503 и `{"status":"unavailable"}`. После закрытия слушателя клиент видит ошибку подключения. Прочие пути — 404, другие методы для `/healthz` — 405. Технический `GET /metrics` слушает отдельный внутренний порт 9091 и не считается пользовательской командой. В тестах ветка 503 воспроизводится подменой внутренней готовности без дополнительной публичной команды.

**Rationale**: HTTP даёт простой проверяемый контракт для мониторинга. Отдельный порт сохраняет единственность публичной команды и не раскрывает метрики наружу. Тело запроса для health-check игнорируется; бизнес-состояние сервиса не меняется, а технический счётчик вызовов обновляется.

**Alternatives considered**: RPC добавляет схему и инфраструктуру; метрики на публичном порту расширяют внешнюю поверхность.

**Source**: [Go net/http ServeMux patterns](https://pkg.go.dev/net/http#ServeMux).

## 3. Учёт вызовов и RPS

**Decision**: Экспортировать `cabby_gateway_health_checks_total{outcome="success|failure"}` как счётчик; обе серии инициализировать нулём. Считать каждый запрос, дошедший до обработчика health-check, после определения результата. Prometheus опрашивает `/metrics` раз в 15 секунд. Grafana показывает три линии: `rate(...[1m])` для каждого исхода и сумму, с шагом графика 1 минута.

**Rationale**: Счётчик и `rate` — стандартная модель Prometheus для частоты событий. Нулевые серии позволяют видеть подтверждённый ноль без первого запроса. Счётчик переживает локальные колебания нагрузки, а `rate` учитывает его сброс после рестарта.

**Alternatives considered**: Gauge с текущим RPS не сохраняет корректный смысл при сбоях сбора; собственные календарные минутные счётчики усложняют сервис. Точное число событий в каждой минуте нельзя восстановить из периодических снимков счётчика при произвольных всплесках, поэтому критерий SC-003 уточнён для равномерной контрольной нагрузки.

**Sources**: [Prometheus instrumentation](https://prometheus.io/docs/practices/instrumentation/), [query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/), [configuration](https://prometheus.io/docs/prometheus/latest/configuration/configuration/).

## 4. Ноль и отсутствие данных

**Decision**: Запросы графика показывают RPS только при успешных scrape в пределах всего минутного окна, используя `up` как условие. Не подменять пустой результат нулём; отключить соединение разрывов линии в Grafana. При восстановлении сбора график возобновляется после появления полного окна.

**Rationale**: Ноль означает, что серия наблюдалась без прироста; отсутствие `up` или неудачный scrape не доказывают отсутствия запросов.

**Alternatives considered**: `or vector(0)` маскирует сбой сбора; одна лишь проверка текущего `up` может отобразить неполное окно после восстановления.

**Sources**: [Prometheus query basics](https://prometheus.io/docs/prometheus/latest/querying/basics/), [Grafana time series](https://grafana.com/docs/grafana/latest/visualizations/panels-visualizations/visualizations/time-series/).

## 5. Локальный запуск и воспроизводимость

**Decision**: Docker Compose для cabby-gateway, Prometheus и Grafana; конфигурации scrape, источника данных и панели хранятся в репозитории. Внешние порты привязаны к loopback для локального запуска; внутренний порт метрик доступен только внутри сети Compose. Пароль Grafana задаётся через локальный файл окружения, отсутствующий в Git. Версии образов Prometheus и Grafana закрепляются при реализации, без плавающего `latest`.

**Rationale**: Один запуск поднимает сервис и готовый график; сохранение конфигурации делает проверку воспроизводимой.

**Alternatives considered**: Ручная настройка Grafana не обеспечивает повторяемый quickstart; установка локальных бинарников требует больше шагов.

**Sources**: [Docker Compose](https://docs.docker.com/compose/), [Grafana provisioning](https://grafana.com/docs/grafana/latest/administration/provisioning/).
