# Implementation Plan: cabby-gateway health-check и график RPS

**Branch**: `feature/basic_gateway` | **Date**: 2026-09-23 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/001-gateway-health-monitoring/spec.md`

## Summary

Создать минимальный HTTP-сервис cabby-gateway на Go 1.26.1 с единственной публичной командой `GET /healthz`. Сервис экспортирует счётчик проверок по исходу на внутреннем порту. Docker Compose поднимает сервис, Prometheus и Grafana с заранее настроенным графиком RPS. Использовать периодический опрос и минутное окно; показывать разрыв вместо нуля при потере данных. Решения и ограничения описаны в [research.md](research.md).

## Technical Context

**Language/Version**: Go 1.26.1.

**Primary Dependencies**: Стандартный `net/http`; `github.com/rs/zerolog` для структурированных JSON-логов; `prometheus/client_golang` для экспорта метрик; Docker Compose, Prometheus, Grafana для локального наблюдения. Версии зависимостей и контейнерных образов закрепить при реализации.

**Storage**: Бизнес-данных и хранилища сервиса нет. Prometheus хранит временные ряды в собственном Docker volume; Grafana хранит локальное состояние в Docker volume, а источник данных и dashboard задаются файлами.

**Testing**: `go test ./...`, `go vet ./...`, проверки HTTP-контракта и счётчика, `docker compose config`, end-to-end запуск трёх контейнеров и контроль графика; нагрузочная проверка 100 запросов/с в течение 5 минут.

**Target Platform**: Linux-контейнеры Docker и локальный запуск gateway через Makefile с Go 1.26.1.

**Project Type**: Backend web service + локальная инфраструктура наблюдения.

**Performance Goals**: 100 health-check запросов/с в течение 5 минут; не менее 99% ответов за 1 секунду; обновление графика не позднее 2 минут после интервала.

**Constraints**: Только одна публичная команда; никакой зависимости health-check от Prometheus или Grafana; без аутентификации для health-check, но технические метрики не публикуются наружу; не записывать секреты/персональные данные; RPS — оценка по скользящему окну 60 секунд.

**Scale/Scope**: Один экземпляр cabby-gateway в первом запуске, два исхода health-check, три линии на одном графике. При масштабировании запросы к метрикам и агрегирование должны охватывать каждый экземпляр отдельно.

### Поведение при отказах и развёртывание

- Если cabby-gateway не отвечает, клиент проверки видит ошибку подключения или таймаут; успешный ответ не формируется.
- После начала корректной остановки gateway переводится в состояние неготовности до закрытия публичного слушателя. Если запрос достигает обработчика в этот промежуток либо обработка завершается внутренней ошибкой, возвращается 503, увеличивается счётчик неуспешных вызовов и пишется структурированное сообщение с временем и типом ошибки. После закрытия слушателя клиент получает ошибку соединения или таймаут.
- В тестах готовность подменяется внутри процесса для воспроизводимой проверки 503 и счётчика `failure`; отдельной публичной команды или режима отказа для операторов нет. На обычном стенде линия `failure` может оставаться нулевой, поэтому её ненулевое значение подтверждается тестом обработчика и счётчика, а наличие линии — конфигурацией dashboard.
- Недоступность Prometheus/Grafana не меняет результат health-check. График в это время показывает отсутствие данных.
- Сначала можно запустить cabby-gateway, затем Prometheus и Grafana; в Compose они поднимаются вместе. После появления полного минутного окна dashboard начинает показывать RPS. Возврат к старой версии не требует миграции данных.
