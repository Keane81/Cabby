# Data Model: cabby-gateway health-check

Сервис не хранит бизнес-данные или историю отдельных запросов. Модель ниже описывает краткоживущую обработку и агрегированные показатели.

## HealthCheckCall

| Поле | Тип | Правило |
|---|---|---|
| `received_at` | момент времени | Устанавливается при поступлении команды; используется для диагностики ошибок, не сохраняется как отдельная запись. |
| `outcome` | `success` или `failure` | Определяется один раз после обработки. |

Один запрос `GET /healthz`, дошедший до обработчика, создаёт один логический вызов. Любой повторный запрос — новый вызов. Другие пути, методы и scrape метрик не создают `HealthCheckCall`.

**Переходы**: `received → success` (200) при готовности или `received → failure` (503) при неготовности/внутреннем отказе. Для одного вызова возможен только один конечный исход и одно увеличение соответствующего счётчика. Ошибка соединения до сервиса не создаёт вызов. При корректной остановке готовность снимается до закрытия слушателя.

## HealthCheckCounter

| Поле | Тип | Правило |
|---|---|---|
| `outcome` | фиксированное значение | Только `success` или `failure`; обе серии существуют с нулём с запуска. |
| `total` | неотрицательное целое | Увеличивается на один для каждого завершённого вызова данного исхода; сбрасывается при рестарте процесса. |

Счётчик агрегирует `HealthCheckCall` по исходу. Идентификаторы пользователей, динамические пути и текст ошибок не используются как labels. Prometheus получает текущие значения периодически и хранит временной ряд.

## RPSPoint

| Поле | Тип | Правило |
|---|---|---|
| `observed_at` | момент времени | Время точки на графике. |
| `window` | длительность | Скользящие 60 секунд. |
| `success_rps` | число ≥ 0 или отсутствие данных | Оценка частоты успешных вызовов. |
| `failure_rps` | число ≥ 0 или отсутствие данных | Оценка частоты неуспешных вызовов. |
| `total_rps` | число ≥ 0 или отсутствие данных | Сумма двух исходов только при полном пригодном окне наблюдения. |

Точки вычисляются на стороне наблюдения из `HealthCheckCounter`; сервис их не хранит. Ноль допустим при наблюдаемом счётчике без прироста. Если сбор данных нарушен, значение отсутствует, чтобы график показал разрыв.

## Связь с требованиями

- FR-001–FR-004: обработка и исход `HealthCheckCall`.
- FR-005: инкремент `HealthCheckCounter` ровно один раз на вызов.
- FR-006–FR-007: производный `RPSPoint` и график.
- FR-008: диагностическое сообщение только для ошибки, без персональных данных и секретов.
