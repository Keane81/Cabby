# Внешний контракт cabby-gateway — руководство

Руководство для внешних клиентов cabby-gateway. Машиночитаемое определение — [openapi.yaml](openapi.yaml) (OpenAPI 3.1). Канонический runtime-файл — `backend/cabby-gateway/api/openapi.yaml`; он встраивается в сервис и отдаётся по `GET /openapi.yaml`. При расхождении руководства и OpenAPI-документа источником истины является OpenAPI-документ.

## 1. Назначение и границы

Контракт описывает единственный опубликованный интерфейс cabby-gateway для внешних клиентов — систем и приложений вне сервиса (включая будущие web/iOS/Android и партнёров). Внешние клиенты интегрируются только через этот контракт и не имеют доступа к внутреннему устройству сервиса или его хранилищам.

На текущем этапе:

- единственная доступная бизнес-операция — **health-check** (`GET /healthz`);
- прочие бизнес-операции внешним клиентам **недоступны**;
- доступ **анонимный** — учётные данные не требуются;
- внутренний интерфейс метрик (`GET /metrics`, порт 9091) **не входит** во внешний контракт и не публикуется; на публичном порту `/metrics` возвращает 404 `unknown_operation`.

## 2. Получение контракта (discovery)

Контракт публикуется двумя способами:

1. **Артефакт репозитория**: `backend/cabby-gateway/api/openapi.yaml` и это руководство.
2. **Runtime**: `GET /openapi.yaml` на публичном порту возвращает текущий документ (`Content-Type: text/yaml; charset=utf-8`).

`GET /openapi.yaml` — единственный авторитетный перечень доступных операций и их версии. Это metadata-эндпоинт, а не бизнес-операция: он не учитывается в счётчике health-check и не имеет побочных эффектов.

## 3. Версия контракта

- Версия — `info.version` в OpenAPI-документе, по SemVer. Текущая версия: **1.0.0**.
- Пути операций не содержат префикса версии (`/healthz` сохраняется для совместимости с уже зафиксированным контрактом health-check).
- Отдаваемый документ всегда соответствует текущей опубликованной версии; клиент определяет версию из `info.version`.
- Будущая мажорная версия может ввести префикс пути (например, `/v1/...`) с планом миграции.

## 4. Операция health-check

| Свойство | Значение |
|---|---|
| Метод и путь | `GET /healthz` |
| Публичный порт | `CABBY_GATEWAY_PORT` из `backend/cabby-gateway/.env` (без переменной — 8080; локальный пример — 8082) |
| Аутентификация | Не требуется |
| Тело запроса | Не используется; дополнительные данные не меняют результат |
| Изменение состояния | Бизнес-состояние не меняется; технический счётчик вызовов увеличивается |

### Результаты

| Условие | HTTP | Тело | Схема |
|---|---:|---|---|
| Сервис способен обрабатывать команду | 200 | `{"status":"ok"}` | HealthStatus |
| Сервис не готов (корректная остановка) или внутренний отказ обработки | 503 | `{"status":"unavailable"}` | HealthStatus |
| Неверный метод на `/healthz` (включая HEAD) | 405 | конверт Error, `code=method_not_allowed` | Error |
| Сервис не отвечает | ошибка соединения или таймаут | нет ответа | — |

Ответы 200 и 503 используют `Content-Type: application/json` и не содержат внутренних сведений, секретов или персональных данных. Клиент считает успешным только HTTP 200 со `status=ok`; все другие исходы означают, что положительная проверка не подтверждена. Семантика health-check унаследована из спецификации 001 без изменений.

## 5. Единая модель ошибок

Отказы уровня шлюза и ошибки будущих операций возвращают единый конверт:

```json
{ "error": { "code": "<stable_category>", "message": "<human_readable>" } }
```

- `code` — стабильная машиночитаемая категория; `message` — человекочитаемое описание без секретов, внутренних сведений и персональных данных.
- HTTP-статус — первичный индикатор категории; `code` уточняет её для программной обработки.

Текущие категории:

| `code` | HTTP | Когда |
|---|---:|---|
| `unknown_operation` | 404 | Запрошен путь, не описанный в контракте. |
| `method_not_allowed` | 405 | Метод не поддерживается для описанного пути (включая HEAD на `/healthz`). |

Конверт `Error` применяется к отказам на неописанные пути/методы и к ошибкам будущих операций. Ответы 200/503 самой операции health-check используют схему `HealthStatus` и не изменяются. Такое разделение позволяет отличать временную неготовность операции (503) от постоянного отсутствия операции (404 `unknown_operation`).

> Примечание о совместимости: ранее (спецификация 001) тела 404/405 были plain-text. HTTP-коды не изменились, выпущенных клиентов нет, поэтому переход 404/405 на единый JSON-конверт обратно совместим и расширяет, а не ломает контракт 001.

## 6. Совместимость и эволюция

- **patch** — уточнения без изменения поведения.
- **minor** — аддитивные изменения: новые операции, новые необязательные поля, новые `code` ошибок. Обратно совместимы.
- **major** — ломающие изменения: требуют плана миграции и информирования затронутых клиентов; возможен новый префикс пути.

Обязательства клиента:

- корректно обрабатывать отсутствие необязательных полей;
- толерантно относиться к неизвестным полям и неизвестным `code` ошибок;
- интегрироваться против конкретной версии контракта и уметь её определить.

Изменения контракта должны сохранять работоспособность выпущенных клиентов либо сопровождаться планом миграции.

## 7. Безопасность и данные

- Доступ к операциям внешнего контракта анонимный; аутентификация/авторизация будут определены отдельной спецификацией при появлении бизнес-операций, затрагивающих данные пользователей.
- Контракт и тела ответов не содержат секретов и персональных данных.
- Внутренние технические интерфейсы (метрики) не публикуются внешним клиентам.
