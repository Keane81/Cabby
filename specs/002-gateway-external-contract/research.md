# Research: опубликованный внешний контракт cabby-gateway

Документ фиксирует решения Phase 0 для спецификации [spec.md](spec.md). Все пункты Technical Context определены; неразрешённых `NEEDS CLARIFICATION` нет — три критических решения (объём, доступ, форма) приняты с пользователем на этапе спецификации.

## 1. Формат машиночитаемого контракта

**Decision**: Использовать OpenAPI 3.1 в YAML как единственный машиночитаемый формат внешнего контракта. Канонический файл — `backend/cabby-gateway/api/openapi.yaml`. Документ описывает только публичный интерфейс внешнего клиента и не включает внутренний интерфейс метрик.

**Rationale**: OpenAPI — отраслевой стандарт описания HTTP API, который удовлетворяет требованию «машиночитаемая форма (стандартный формат описания API)» без привязки к конкретному вендору. YAML удобен для ревью и версионирования в Git. Стандартная экосистема (валидаторы, генераторы клиентов, Swagger UI/Redocly) позволяет внешним клиентам проверять интеграцию до обращения к сервису (SC-006) и генерировать код.

**Alternatives considered**: JSON Schema отдельно от OpenAPI — описывает только структуры, но не операции и не способы вызова; gRPC/Protobuf IDL — добавляет схему и инфраструктуру и не нужен для HTTP-команды; собственный формат — не поддерживается инструментами клиентов. OpenAPI в JSON — валиден, но менее удобен для авторинга и ревью; выбран YAML.

**Sources**: [OpenAPI Specification 3.1](https://spec.openapis.org/oas/v3.1.0), [OpenAPI Initiative](https://www.openapis.org/).

## 2. Публикация и обнаружение контракта (discovery)

**Decision**: Контракт публикуется двумя способами: (а) как артефакт в репозитории (`backend/cabby-gateway/api/openapi.yaml` и руководство `specs/002-gateway-external-contract/contracts/external-api.md`); (б) сервис отдаёт его по стабильному пути `GET /openapi.yaml` на публичном порту. Канонический YAML встраивается в бинарник через `go:embed` и отдаётся как есть с `Content-Type: text/yaml; charset=utf-8`. Обнаружение возможностей — через сам документ: он является единственным авторитетным перечнем операций (FR-011).

**Rationale**: «Контракт для внешних клиентов» подразумевает, что клиент может его получить. Well-known URL — стандартный механизм публикации, удовлетворяющий FR-011 (обнаружение через контракт) и FR-007 (определение версии: `info.version` в полученном документе). `go:embed` исключает расхождение между отданным документом и содержимым бинарника и не требует файловой системы в рантайме. Отдача YAML напрямую избегает зависимости для конвертации в JSON; инструменты OpenAPI принимают YAML-URL.

**Alternatives considered**: Только артефакт в репозитории — внешним клиентам нужен доступ к репозиторию/релизу, что слабее отвечает «published contract»; конвертация YAML→JSON в рантайме и отдача `/openapi.json` — добавляет зависимость (`gopkg.in/yaml.v3`) без необходимости, так как YAML валиден для OpenAPI-инструментов; отдельный docs-UI (Swagger UI) — расширяет публичную поверхность и не требуется для MVP.

**Risk**: Путь `/openapi.yaml` становится новым публичным путём; прежде все пути кроме `/healthz` возвращали 404. Изменение аддитивно и обратно совместимо (см. раздел 6).

**Sources**: [go:embed](https://pkg.go.dev/embed), [OpenAPI document formats](https://spec.openapis.org/oas/v3.1.0#document-structure).

## 3. Версионирование контракта

**Decision**: Версия контракта — `info.version` в OpenAPI-документе по SemVer, начиная с `1.0.0`. Путь operations не содержит префикса версии (`/healthz` сохраняется). Отдаваемый документ всегда соответствует текущей опубликованной версии; клиент определяет версию из `info.version`. Будущая мажорная версия MAY ввести префикс пути (например, `/v1/...`) с планом миграции.

**Rationale**: SemVer — понятное соглашение для гарантий совместимости (FR-007, FR-008, Principle II). Сохранение `/healthz` без префикса избегает нарушения уже зафиксированного контракта спецификации 001. Версия в `info.version` — стандартное, не требующее额外 инфраструктуры место для идентификации.

**Alternatives considered**: Версия в URL с первого выпуска (`/v1/healthz`) — сломала бы существующий путь из spec 001; версия только в имени файла/теге Git — клиент не может определить версию в рантайме; заголовок `X-Cabby-Contract-Version` — возможен как дополнение, но `info.version` уже удовлетворяет FR-007, поэтому заголовок не вводится, чтобы не расширять поверхность.

**Sources**: [Semantic Versioning 2.0.0](https://semver.org/), [OpenAPI info object](https://spec.openapis.org/oas/v3.1.0#info-object).

## 4. Единая модель ошибок

**Decision**: Ввести единый конверт ошибки для отказов уровня шлюза и будущих операций:

```json
{ "error": { "code": "<stable_category>", "message": "<human_readable>" } }
```

- `code` — стабильная машиночитаемая категория (фиксированный набор, расширяется аддитивно). На текущем этапе: `unknown_operation` (HTTP 404 для неописанных путей), `method_not_allowed` (HTTP 405 для неверного метода).
- `message` — человекочитаемое описание; MUST NOT содержать секреты, сведения о внутреннем устройстве или персональные данные (FR-005, Principle IV).
- HTTP-статус остаётся первичным индикатором категории; `code` уточняет её для программной обработки.

Ответы самой операции health-check (200 `{"status":"ok"}` и 503 `{"status":"unavailable"}`) НЕ изменяются и используют схему `HealthStatus`, унаследованную из спецификации 001. Конверт `Error` применяется к отказам на неописанные пути/методы и к ошибкам будущих операций.

**Rationale**: Спецификация требует, чтобы клиент мог программно определить категорию отказа (US2, FR-005), а непредвиденный запрос получал «предсказуемый отказ в едином формате». Текущие plain-text тела `http.NotFound` (`404 page not found`) и `http.Error(..., 405)` не соответствуют единому формату. Структурированный конверт с фиксированным `code` решает это. Сохранение тел 200/503 health-check без изменений выполняет допущение спецификации («семантику ... публикует без изменений») и SC-004 (обратная совместимость).

**Alternatives considered**: Плоская форма `{ "code", "message" }` — проще, но менее расширяема и смешивается с полезной нагрузкой операции; RFC 7807 `application/problem+json` — стандартен, но тяжелее для MVP и меняет media type; привести 503 health-check к конверту `Error` — нарушило бы «без изменений» семантики health-check, поэтому отклонено.

**Risk**: Изменение тел 404/405 с plain-text на JSON меняет документированное в spec 001 поведение («Любой другой путь возвращает 404»). HTTP-коды не меняются, выпущенных клиентов нет (spec 001: «выпущенных клиентов нет»), поэтому изменение обратно совместимо; контракт 001 расширяется, а не ломается. См. раздел 6.

**Sources**: [RFC 7807 Problem Details](https://www.rfc-editor.org/rfc/rfc7807), [OpenAPI responses](https://spec.openapis.org/oas/v3.1.0#responses-object).

## 5. Аутентификация и поверхность

**Decision**: Доступ к операциям внешнего контракта анонимный (FR-006). Внутренний интерфейс метрик (`GET /metrics`, порт 9091) не включается во внешний контракт и не публикуется внешним клиентам (FR-010); на публичном порту путь `/metrics` возвращает 404 `unknown_operation`. Аутентификация/авторизация откладываются до появления бизнес-операций и будут определены отдельной спецификацией.

**Rationale**: Соответствует выбранному объёму («анонимно, без auth») и Principle IV (минимально необходимые права; метрики остаются внутри). Health-check по назначению анонимен и не работает с пользовательскими данными.

**Alternatives considered**: Требовать API-ключ уже сейчас — избыточно для единственной анонимной технической команды и не согласуется с решением пользователя; публиковать метрики наружу — расширяет поверхность и нарушает FR-010.

## 6. Совместимость, публикация и развёртывание

**Decision**: Политика совместимости фиксируется в руководстве и в OpenAPI `info.description`:
- **patch** — уточнения без изменения поведения;
- **minor** — аддитивные изменения (новые операции, новые необязательные поля, новые `code` ошибок) — обратно совместимы;
- **major** — ломающие изменения — требуют плана миграции и информирования клиентов (FR-008, Principle II); MAY сопровождаться новым префиксом пути.

Клиенты MUST корректно обрабатывать отсутствие необязательных полей и неизвестные поля/коды (Principle II). Канонический runtime-файл — `backend/cabby-gateway/api/openapi.yaml`; копия в `specs/002-gateway-external-contract/contracts/openapi.yaml` — проектный эталон, реализуемый в канонический путь. Тест parity подтверждает, что отданный документ совпадает с закоммиченным каноническим файлом, исключая дрейф.

Порядок развёртывания: изменение аддитивно (новый путь `/openapi.yaml`, формат тел 404/405). Сначала публикуется контракт и руководство, затем код шлюза; существующее поведение `/healthz` не меняется. Откат — удаление обработчика контракта восстанавливает прежнее поведение «все пути кроме /healthz → 404»; миграция данных не требуется.

**Rationale**: Явная политика версионирования и parity-тест выполняют Principle II и SC-004/SC-005, предотвращая расхождение документа и реализации.

**Alternatives considered**: Держать контракт только в спеке без parity-теста — риск дрейфа между документом и сервисом; генерировать OpenAPI из кода — добавляет инструмент генерации, избыточно для одной команды.

**Sources**: [SemVer](https://semver.org/), конституция Cabby, принципы II и IV.

## 7. Влияние на код шлюза (объём реализации)

**Decision**: Минимальные аддитивные изменения публичного обработчика:
- добавить отдачу встроенного OpenAPI-документа по `GET /openapi.yaml`;
- заменить plain-text тела 404/405 на единый конверт `Error` (JSON);
- тела 200/503 `/healthz` и поведение счётчика метрик не изменяются;
- путь `/openapi.yaml` не учитывается в счётчике health-check и не считается бизнес-операцией.

Публичный обработчик эволюционирует из одиночного `http.HandlerFunc` с проверкой пути в небольшой маршрутизатор (явный switch по пути/методу или `http.ServeMux`), сохраняя явный запрет HEAD на `/healthz`.

**Rationale**: Изменения точно покрывают требования внешнего контракта (публикация, discovery, единая модель ошибок) без затрагивания семантики health-check и мониторинга из spec 001.

**Alternatives considered**: Не менять код и опубликовать контракт только артефактом — не даёт runtime-discovery и не приводит 404/405 к единому формату (US2/FR-005); полноценный роутер-фреймворк — избыточен.
