# Data Model: внешний контракт cabby-gateway

Сервис не хранит бизнес-данные. Модель описывает сущности опубликованного контракта и структуры ответов, которые фиксирует контракт. Каноническое машиночитаемое определение — [contracts/openapi.yaml](contracts/openapi.yaml); правила использования — [contracts/external-api.md](contracts/external-api.md).

## ContractDocument

Единственный авторитетный перечень операций внешнего интерфейса (FR-001, FR-011).

| Поле | Тип | Правило |
|---|---|---|
| `version` | строка SemVer | Идентификатор опубликованной версии (`info.version`); начальное значение `1.0.0`. |
| `operations` | набор Operation | Полный список операций, доступных внешним клиентам; на текущем этапе ровно одна. |
| `error_model` | ErrorModel | Единая модель отказа, применяемая к неописанным путям/методам и будущим операциям. |
| `compatibility_policy` | CompatibilityPolicy | Правила изменения и гарантии для выпущенных клиентов. |

Документ публикуется как артефакт репозитория и отдаётся сервисом по `GET /openapi.yaml`. Отданный документ MUST совпадать с закоммиченным каноническим файлом (parity). Внутренний интерфейс метрик в документ не входит (FR-010).

## ContractVersion

| Поле | Тип | Правило |
|---|---|---|
| `semver` | `MAJOR.MINOR.PATCH` | Определяет гарантии совместимости. |

**Переходы**: `patch` — уточнение без изменения поведения; `minor` — аддитивное изменение (новая операция, новое необязательное поле, новый `code` ошибки), обратно совместимо; `major` — ломающее изменение, требует плана миграции и информирования клиентов (FR-008). Клиент определяет целевую версию из `version` полученного документа (FR-007).

## Operation

Отдельная команда, доступная внешнему клиенту (FR-003, FR-004).

| Поле | Тип | Правило |
|---|---|---|
| `name` / `operation_id` | строка | Уникальный идентификатор в пределах контракта. |
| `method` | HTTP-метод | Способ вызова. |
| `path` | строка | Путь без префикса версии на текущем этапе (`/healthz`). |
| `auth` | `anonymous` | На текущем этапе доступ без учётных данных (FR-006). |
| `success_responses` | набор | Документированные успешные результаты. |
| `error_responses` | набор | Документированные отказы (включая единый ErrorModel). |
| `side_effects` | описание | Health-check не меняет бизнес-состояние; допускается технический учёт вызова. |

**Текущая операция — health-check** (унаследована из спецификации 001, семантика не меняется):

| Условие | HTTP | Тело | Схема |
|---|---:|---|---|
| Сервис способен обрабатывать команду | 200 | `{"status":"ok"}` | HealthStatus |
| Сервис не готов (корректная остановка) или внутренний отказ обработки | 503 | `{"status":"unavailable"}` | HealthStatus |
| Неверный метод на `/healthz` (включая HEAD) | 405 | конверт Error, `code=method_not_allowed` | Error |
| Неописанный путь | 404 | конверт Error, `code=unknown_operation` | Error |

Клиент считает положительным только HTTP 200 со `status=ok`; все прочие исходы означают, что положительная проверка не подтверждена.

## HealthStatus

| Поле | Тип | Правило |
|---|---|---|
| `status` | `ok` \| `unavailable` | Единственное поле; других полей нет. |

Ответы 200 и 503 используют `Content-Type: application/json`. Тело не содержит внутренних сведений, секретов или персональных данных.

## ErrorModel

Единый конверт отказа (FR-005, FR-012).

| Поле | Тип | Правило |
|---|---|---|
| `error.code` | строка из фиксированного набора | Стабильная машиночитаемая категория; расширяется аддитивно (minor). |
| `error.message` | строка | Человекочитаемое описание; без секретов, внутренних сведений и персональных данных. |

**Категории (`code`) на текущем этапе**:

| `code` | HTTP | Значение |
|---|---:|---|
| `unknown_operation` | 404 | Запрошен путь, не описанный в контракте. |
| `method_not_allowed` | 405 | Метод не поддерживается для описанного пути (включая HEAD на `/healthz`). |

HTTP-статус — первичный индикатор категории; `code` уточняет её для программной обработки. Клиент MUST корректно обрабатывать неизвестные `code` и отсутствие необязательных полей (Principle II). ErrorModel отличает временную неготовность операции (503 HealthStatus для health-check) от постоянного отсутствия операции (404 `unknown_operation`) — FR-012.

## CompatibilityPolicy

| Правило | Содержание |
|---|---|
| Аддитивные изменения | Новые операции, необязательные поля и `code` ошибок — minor, обратно совместимы. |
| Ломающие изменения | Требуют major, плана миграции и информирования затронутых клиентов (FR-008). |
| Обязательства клиента | Обрабатывать отсутствие необязательных полей, неизвестные поля и ожидаемые ошибки (FR-009). |
| Источник истины | Канонический `backend/cabby-gateway/api/openapi.yaml`; расхождение документа и реализации считается дефектом (SC-005). |

## Связь с требованиями

- FR-001, FR-011: ContractDocument как единственный авторитетный перечень операций.
- FR-002: ContractDocument (машиночитаемый openapi.yaml) + external-api.md (руководство); источник истины определён.
- FR-003, FR-004: Operation; единственная операция — health-check, прочие явно недоступны.
- FR-005, FR-012: ErrorModel и категории отказов.
- FR-006: Operation.auth = anonymous.
- FR-007, FR-008: ContractVersion и CompatibilityPolicy.
- FR-009: обязательства клиента в CompatibilityPolicy.
- FR-010: внутренний интерфейс метрик исключён из ContractDocument.
