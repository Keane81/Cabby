# Implementation Plan: Эмулятор парка кабберов для нагрузочного прогона

**Branch**: `feature/hl_beginning` (каталог спецификации `005-cabber-fleet-emulator`) | **Date**: 2026-10-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/005-cabber-fleet-emulator/spec.md`

## Summary

Новый Go-модуль `backend/emulator` — консольный инструмент разработчика (не сервис): одна команда запускает парк виртуальных кабберов, каждый из которых по публичному REST-контракту gateway проходит цикл «регистрация → вход → периодическая отправка координат → выход». Один процесс держит до 50 000 кабберов как лёгкие горутины поверх общего HTTP-клиента с ограниченным пулом соединений; при необходимости тот же бинарник запускается в нескольких экземплярах (`-instance`/`-instances` делят индексы кабберов). Движение — случайное блуждание с ограниченной скоростью в прямоугольной области. Показатели (активные кабберы, отправки/с, ошибки, задержки) печатаются раз в несколько секунд, итоговая сводка — в stdout и в JSON-файл для сравнения прогонов. Публичный контракт, gateway, `auth` и `location` не меняются. Данные эмулятора не удаляются (Clarifications).

Главный риск плана — не отправка координат, а **массовый вход**: `auth` хеширует пароль argon2id с двумя параллельными вычислениями, и регистрация плюс вход 50 000 кабберов занимают десятки минут (R-03). Поэтому разгон — отдельная, честно измеряемая фаза со своей сводкой.

## Technical Context

**Language/Version**: Go 1.26.1 (как в остальных модулях)

**Primary Dependencies**: стандартная библиотека (`net/http`, `context`, `flag`, `encoding/json`, `math/rand/v2`, `os/signal`) и `github.com/rs/zerolog` для служебных сообщений. Без `contracts`, `platform`, `lifecycle`: эмулятор ходит только по HTTP и сервисом не является (см. Constitution Check, отступление от шаблона сервиса).

**Storage**: N/A. Нагрузка пишет в существующие БД `auth` и `location` через gateway; сводка прогона — JSON-файл в рабочем каталоге.

**Testing**: `go test` и `go test -race` с фейковым gateway на `httptest` (разгон, расписание, повторный вход, остановка, ошибки, утечки в логи); детерминированные тесты маршрута (границы, скорость). Сквозная проверка — `make emulate` на живом стеке (quickstart).

**Target Platform**: macOS и Linux хост разработчика; цель — опубликованный порт gateway локального compose-стека (`127.0.0.1:${CABBY_GATEWAY_PORT}`).

**Project Type**: CLI-инструмент в backend-монорепозитории (отдельный Go-модуль).

**Performance Goals**: до 50 000 одновременно активных кабберов; суммарная частота отправок — по профилю (при интервале 5 с ≈ 10 000 отправок/с), отклонение от заданной не более 10% (SC-002). Окно отправки каждого каббера равномерно сдвинуто по фазе. Расход ресурсов самого эмулятора: ≤ 1 ГиБ RSS и ≤ 1,5 ядра CPU на 50 000 кабберов (проверяется замером, R-02).

**Constraints**: ограниченный пул соединений (по умолчанию 512), поднятие лимита файловых дескрипторов при старте и ранняя ошибка, если его не хватает; неудавшаяся отправка координат не повторяется (Clarifications); одновременных запросов регистрации/входа не больше 8 (константа, R-03); без повторов отправки, но с ограниченными повторами входа (R-04); пароли, токены, email и координаты не попадают в журналы и сводки (FR-015); по умолчанию адрес только локальный (FR-016).

**Scale/Scope**: 1 новый модуль (около 8 пакетов), правка `backend/Makefile` (`MODULES`) и корневого `Makefile` (цель `emulate`); ни одной новой публичной операции и ни одного изменения compose.

## Constitution Check

*GATE: Must pass before Phase 0 research. Re-check after Phase 1 design.*

| Принцип | Статус | Обоснование |
|---|---|---|
| I. Явные границы и ответственность | PASS | Эмулятор — клиент, как web/iOS/Android: обращается только к опубликованному REST-контракту gateway, не знает про `auth`, `location` и их БД, не использует `contracts`/`platform`. Бизнес-логики области в нём нет: валидность координат и сессий проверяют сервисы. |
| II. Совместимые контракты | PASS | Контракт не меняется: используются `POST /cabbers`, `POST /cabber/session`, `POST /cabber/location`, `DELETE /cabber/session` версии 1.2.0. Эмулятор читает ответы терпимо (лишние поля игнорирует, `401` — сигнал войти заново, `409` при регистрации — сбой уникальности). Новая версия контракта не нужна, поэтому правила AGENTS.md про Bruno и smoke не применяются. |
| III. Устойчивость под нагрузкой | PASS | Эта фича и есть инструмент проверки принципа III для остальных. Сам эмулятор: ожидаемая нагрузка и точки отказа определены (R-02, R-03), у каждого запроса таймаут, повторов отправки нет, повторы входа ограничены, перегрузка самого генератора обнаруживается и сообщается (FR-014). Наблюдаемость — живые показатели и итоговая сводка; метрики Prometheus эмулятор не публикует (R-06). Сквозная трассировка не нужна: `request_id` создаёт gateway. |
| IV. Безопасность и данные | PASS | Секреты и координаты не логируются; пароль эмулируемых кабберов генерируется на прогон и нигде не печатается. Эмулятор по умолчанию бьёт только в loopback-адрес, иначе требует явного флага (FR-016) — защита от случайной нагрузки на чужой стенд. Реальных персональных данных нет: email и имена синтетические с префиксом эмулятора. Хранение и удаление данных эмулятора осознанно вне объёма (Clarifications), долг — в Complexity Tracking. |
| V. Проверяемые изменения на всех платформах | PASS | Затронут только backend (новый модуль); web/iOS/Android не затронуты. Проверки: `make check` (модуль в `MODULES`), юнит- и интеграционные тесты на фейковом gateway, сквозной прогон по quickstart. Критерии приёмки — SC-001…SC-007. |

**Отступление от шаблона сервиса** (AGENTS.md, «Новый backend-сервис»): модуль не сервис — нет gRPC, БД, `/metrics`, слоёв `grpcserver → service → repo`, миграций и записи в `compose.yaml`. Остаются применимыми: отдельный Go-модуль, `zerolog` и логгер значением из `main`, запуск и остановка по сигналу, стартовые и финальные сообщения, добавление в `MODULES`, запрет на значения запросов в логах. Причина и срок пересмотра — Complexity Tracking.

*Повторная проверка после Phase 1: статус не изменился; отступление остаётся единственным.*

```text
│   └── report/                 # живая строка и итоговая сводка (текст и JSON)
├── Makefile                    # run, test, test-race, vet
├── go.mod
└── README.md                   # ссылка на quickstart (короткая)
```

Правки вне модуля: `backend/Makefile` (`MODULES` += `emulator`), корневой `Makefile` (цель `emulate`, `ARGS=`). `compose.yaml`, `deploy/`, Bruno и OpenAPI не меняются.

**Structure Decision**: отдельный модуль `backend/emulator`, потому что у него свой жизненный цикл (запускается вручную, не разворачивается) и он не должен тянуть серверные зависимости монорепозитория. Единственная связь со стеком — публичный HTTP-контракт; это же гарантирует, что нагрузка проходит весь путь клиента.

| Отступление | Зачем | Почему проще нельзя |

| Модуль-CLI без слоёв и метрик шаблона сервиса | Эмулятор — клиентский инструмент, а не сервис; слои, БД и `/metrics` создали бы мёртвый код | Шаблон `backend/location` описывает сервис с БД и gRPC; применить его целиком к CLI значило бы тащить `platform`, `lifecycle` и gRPC без нужды. | Журнал и живая строка пишутся в stderr, а не в stdout, как у сервисов | stdout занят итоговой сводкой и должен оставаться пригодным для конвейера (`jq`, файл) | Логгер в stdout смешал бы строки журнала с сводкой; правило AGENTS.md про stdout написано для сервисов, у которых нет иного вывода. |
| Данные эмулятора копятся без очистки | Решение пользователя (Clarifications) | Очистка требует либо новой операции в публичном контракте, либо доступа к БД в обход сервисов (нарушает принцип I); долг: при 10 000 отправок/с база растёт ≈ 150 ГБ/сутки, то есть ≈ 6 ГБ в час (R-07). Чистая база — `make docker-up-clean`. |
