# Data Model: Эмулятор парка кабберов

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

Эмулятор ничего не хранит в базах: все сущности живут в памяти процесса на время прогона, единственный постоянный след — файл сводки. Данные в `auth` и `location` создаются существующими операциями и описаны в [003](../003-cabber-auth/data-model.md) и [004](../004-cabber-location/data-model.md).

## Profile (профиль нагрузки)

| Поле | Тип | По умолчанию | Правило |
|---|---|---|---|
| `Cabbers` | целое | 100 | 1…50 000 на процесс-кластер; < 1 или > 50 000 — отказ |
| `Interval` | длительность | 5 с | ≥ 100 мс; ≤ 0 — отказ |
| `Duration` | длительность | 0 (до сигнала) | ≥ 0; 0 — без ограничения |
| `RampUp` | длительность | `max(10 с, Cabbers × 25 мс)` | ≥ 0; 0 — все сразу, допускается только явно |
| `Area` | прямоугольник (широта, долгота ×2) | `55.60,37.40,55.90,37.85` | −90…90, −180…180, площадь > 0, обе стороны ≥ 1 км |
| `Target` | URL | `http://127.0.0.1:8080` | не loopback — только с `AllowRemote` |
| `AllowRemote` | флаг | выкл. | — |
| `Seed` | целое | случайное, печатается | воспроизводимость маршрутов и паролей |
| `RunID` | строка 8 символов | случайная, печатается | входит в email |
| `MaxConns` | целое | 512 | ≥ 1 |
| `Instances`, `Instance` | целые | 1, 0 | `0 ≤ Instance < Instances` |
| `ReportPath` | путь | `emulator-report-<RunID>.json` | каталог должен существовать |

Недопустимый профиль отклоняется целиком до первого запроса (FR-009); сообщение называет поле и причину.

## Cabber (эмулируемый каббер)

| Поле | Описание |
|---|---|
| `Index` | номер 0…N−1, определяет email, имя, пароль, начальную позицию и момент входа |
| `Email` | `emu-<RunID>-<Index>@emulator.cabby.test` (канонический вид: нижний регистр) |
| `Name` | `emu-<Index>` |
| `Password` | детерминированная строка из 12 символов; не печатается и не логируется |
| `Token` | bearer-токен текущей сессии; только в памяти |
| `State` | см. ниже |
| `Position` | широта, долгота (float64), в пределах `Area` |
| `Speed`, `Heading` | км/ч (20–50, постоянна) и курс |

**Состояния и переходы**:

```text
Waiting ──(наступил момент разгона)──▶ Registering ──ok──▶ LoggingIn ──ok──▶ Active
   │                                      │ 3 неудачи              │ 3 неудачи     │ 401 на отправке
   │                                      ▼                        ▼               ▼
   │                                    Failed                   Failed       LoggingIn (повторный вход)
   │                                                                              │ 3 неудачи
   └──(сигнал остановки)──▶ Stopped ◀──(сигнал остановки)── Active ──────────────▶ Lost
                              │
                              └──▶ LoggingOut ──▶ Done
```

`Failed` — каббер не запустился; `Lost` — сессия потеряна и вход не удался; оба состояния окончательны и считаются в сводке. Остановка из любого состояния прекращает отправки; `LoggingOut` выполняется только для имеющих сессию.

## Step (точка маршрута)

Широта и долгота (после округления до 7 знаков), момент планирования отправки. Инвариант: расстояние между соседними точками одного каббера ≤ `Speed × Interval` (с допуском на проекцию), все точки внутри `Area`.

## Stats (показатели)

Счётчики (атомарные): `registered`, `logged_in`, `register_failed`, `login_failed`, `relogin`, `active`, `sent_ok`, `sent_failed{kind}`, `skipped`, `logged_out`, `logout_failed`. Виды ошибок отправки (`kind`): `unauthorized`, `invalid_request` (дефект эмулятора), `unavailable` (5xx), `timeout`, `network`. Гистограммы: задержка отправки, задержка регистрации и входа, `dispatch_lag`.

## Report (сводка прогона)

JSON (поля описаны в [contracts/cli.md](./contracts/cli.md)): профиль (без секретов), время старта/окончания, фазы, итоговые счётчики, фактическая и целевая частота отправок, время до полного парка, доля кабберов, начавших вовремя, перцентили задержек (p50/p95/p99/max), число не вышедших сессий, оценка прироста БД, вердикт самоконтроля (`ok` / `generator_saturated` / `system_saturated`).
