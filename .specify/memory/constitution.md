# Конституция Cabby

<!-- Spec Kit constitution: правила для спецификаций, планов, задач и ревью. -->

**Версия:** 1.0.0

**Принята:** 2026-09-23

**Последнее изменение:** 2026-09-23

## Принципы

### I. Явные границы и ответственность

Каждый backend-сервис MUST владеть своей бизнес-областью и данными. Другие сервисы MUST обращаться к нему через опубликованный контракт, а не напрямую к его хранилищу. Общий код в монорепозитории SHOULD содержать только действительно общие контракты и утилиты; бизнес-логика остаётся у владельца области. Для web, iOS и Android MUST быть ясно, какие API и сценарии они используют.

### II. Совместимые контракты

Изменения API, событий и форматов данных MUST быть совместимы с уже выпущенными клиентами либо сопровождаться планом миграции. Спецификация изменения MUST описывать затронутые сервисы и платформы, поведение при ошибках и порядок развёртывания. Клиенты MUST корректно обрабатывать отсутствие необязательных полей и ожидаемые ошибки.

### III. Устойчивость под нагрузкой

Для критичных backend-сценариев план MUST указывать ожидаемую нагрузку, задержки, точки отказа и способ проверки этих допущений. Межсервисные вызовы MUST иметь таймауты и ограниченные повторные попытки; операции с повторной доставкой MUST быть идемпотентными там, где это необходимо для корректности. Изменения MUST предусматривать наблюдаемость: метрики, структурированные логи и трассировку через границы сервисов.

### IV. Безопасность и данные

Доступ MUST проверяться на сервере по принципу минимально необходимых прав. Секреты и персональные данные MUST не попадать в исходный код и диагностические сообщения. Хранение и передача чувствительных данных MUST соответствовать требованиям, принятым для проекта; при отсутствии таких требований их нужно определить до реализации соответствующего сценария.

### V. Проверяемые изменения на всех платформах

Каждое изменение MUST иметь проверяемые критерии приёмки. План MUST назвать затронутые части монорепозитория — backend, web, iOS, Android — и необходимые проверки для каждой из них. Критичные пользовательские и межсервисные сценарии MUST покрываться тестами на подходящем уровне; исправление дефекта SHOULD включать проверку, воспроизводящую его.

## Управление

Конституция применяется к новым спецификациям, планам, задачам и ревью. Если решение отступает от принципа, план MUST зафиксировать причину, риск и срок пересмотра. Изменения конституции принимаются через ревью в репозитории с описанием влияния на существующие решения. Версия меняется по SemVer: major — изменение или удаление принципа, minor — новый принцип, patch — уточнение без изменения смысла.
